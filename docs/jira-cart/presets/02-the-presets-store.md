# 02 — The fourth key exists before anything reads it

**Lands nothing visible.** A new storage key, its normalisation, the first-run build
from today's preferences, and `store-smoke` over the hostile values. No UI change,
no format change, **no output byte change**. Everything after this depends on it.

**Needs 01** only for its findings; nothing here waits on a measurement.

**Read first:** ADR **§2.4** in full — the three-keys comment at
`src/jira-cart.user.js:432-441` and the last migration row especially — then the
`DEFAULT_PREFS` / `loadPrefs` / `normalisePrefs` / `savePrefs` /
`normaliseFieldList` block at `src/jira-cart.user.js:925-1180`, and
`test/jira-cart/store-smoke.mjs`. Then [the decision record](README.md), decisions
1 to 5 and 20 to 22.

---

## Which path this is on, and it is the OPPOSITE of the prefs path

§2.4 draws one line through this design: *a preference that does not parse falls
back to the defaults, because a preference is regenerated by clicking a switch. A
collection is not.* And the store's own comment: *"a malformed preference cannot
take a collection with it."*

**Presets are on the collections side of that line, and that is decision 20.** They
are the whole export configuration under names the user typed. A whole-blob fallback
to shipped defaults would read as *you lost every preset you built*, and it would be
a designed behaviour rather than an accident.

So: **repair per entry, never wholesale.** A preset whose field list is rubbish gets
that list repaired. A preset with no usable name is dropped. The rest survive.

**Do not put any of this near `load()`.** That function is the collections path and
carries four migration rows; this is a fourth key with its own reader.

## What to add

### The key

`gt-jira-cart.presets`, beside the three that exist. Same store — `GM_*`, never
`GM.*`, for the reason §2.5 gives: `GM.setValue` is promise-based and an `await` in
a copy handler lands the clipboard write outside its user activation.

### The stored shape

```json
{
  "details": [
    { "id": "…", "name": "Standard", "star": true,
      "lineShape": "markdown",
      "fields": [ { "id": "type", "on": true }, … ] }
  ],
  "report": [
    { "id": "…", "name": "Standard", "star": true,
      "lineShape": "markdown",
      "band1": "priority", "band2": "team",
      "fields": [ … ] }
  ]
}
```

- **`id` is opaque**, `crypto.randomUUID()`, generated once and never derived from
  the name — so a rename is free. Exactly §2.4's reasoning for a collection's id.
- **`star` is a flag on the preset** and not an id stored elsewhere (decision 10).
  `collections` keeps no pointer to the active one either: it is `collections[0]`, so
  *"removing it PROMOTES THE NEXT ONE BY CONSTRUCTION. No id can dangle, because no
  id is stored anywhere."* Presets sort by name, so position cannot carry that, and
  the flag is what replaces it.
- **`band1` / `band2` only on `report`.** A 📋 Details preset has no headings, and a
  key that existed and was never read would be a promise the format does not keep.
- **No stored order.** The list is displayed sorted by name (decision 12), so the
  array's order means nothing. Say so in a comment, or a later session will preserve
  it carefully for no reason.

### `normalisePresets(stored)`, per list

In this order:

1. Not an object → build both lists from scratch (see *first run* below).
2. Not an array for a list → build that list from scratch.
3. Per entry, in order: `name` must be a non-empty string after trimming, else
   **drop the entry**; `id` must be a non-empty string, else mint one; `lineShape`
   through the existing shape vocabulary, else that key's default; `fields` through
   **`normaliseFieldList` unchanged**; on `report`, `band1` and `band2` through the
   existing band rules **including the pair rule** — the two may not name the same
   field, and **band 2 is the one that gives way**, never band 1.
4. Names through `uniqueName` **within the list**, so a hand-edited blob cannot hold
   two presets called `Executive`.
5. **Exactly one `star` per list.** Zero, or two, or a non-boolean → the flag goes to
   the first preset by name and comes off every other. This is the invariant the whole
   feature rests on, so it is enforced on the way in rather than trusted.
6. An **empty** list → build it from scratch. A list with no presets has no answer to
   *what does this button print*, and decision 11 says a list always holds at least
   one. Note this is the **opposite** of configurability decision 23, where an empty
   *field* list is honoured because zero fields is a state somebody clicked their way
   to — zero presets is not, because the last delete is refused.

### First run, which is the only migration

If the key is absent, build one preset per list named **`Standard`**, `star: true`,
carrying the prefs blob's `detailsFields`, `reportFields`, `reportBand1`,
`reportBand2` and `lineShape` **as they are stored right now**.

**The requirement is byte-for-byte silence:** an install that never opens ⚙ must not
be able to tell this shipped. That is the same requirement 1.2.0's defaults carried
and it is the one thing here that is not negotiable.

`Standard` and not `Default` (decision 21): *the default preset* and *the preset
called Default* would be two different things the moment ★ moved.

**The key existing is what says the build has happened.** No flag, no version, no
second value that could disagree.

### And the prefs blob loses four keys

`detailsFields`, `reportFields`, `reportBand1`, `reportBand2` come out of
`DEFAULT_PREFS`. **`lineShape` stays** — it is 🔗 Links' own setting from now on
(decision 4). `normalisePrefs` keeps only known keys, so the four stop being carried
on the next write with nothing to migrate.

**Read the old values before you drop them.** The first-run build above needs them,
so the reader for the four has to outlive their removal from `DEFAULT_PREFS` — a
small function that reads the raw prefs blob directly, used once, with a comment
saying it exists for that and can be deleted when no install can still be on 1.6.0.

`EXPORT_PREF_KEYS` — what `Restore export defaults` reaches — shrinks to
`lineShape`. Ticket 03 gives it the rest of its new meaning.

## What to test, in `store-smoke.mjs`

**Slice the new functions out of the source, never copy them.** The README's rule,
and `store-smoke` is the file that has already been caught breaking it: it carried
`MIN_BLOCK = 160` against the script's `215` and the check was green because it was
measuring the harness's own constant.

- absent key → one `Standard` per list, ★, carrying the prefs values
- absent key **and** absent prefs → one `Standard` per list from the shipped values
- `null`, a number, a string, an array at the root → both lists rebuilt
- a list that is not an array → that list rebuilt, **the other one kept**
- an entry with no name, an empty name, a whitespace name → dropped
- an entry with no id → an id minted, everything else kept
- two entries with the same name → `uniqueName` applied inside the list
- **zero stars → the first by name gets it; two stars → only the first by name keeps
  it; `star: "yes"` → not a star**
- an empty list → rebuilt with one `Standard`
- an unknown `lineShape` → that key's default
- `band1: "none"` → the default band back, never `none`
- `band1` and `band2` naming the same field → **band 2** collapses to `none`
- `band1`/`band2` present on a **details** preset → dropped, because that export has
  no headings
- a `fields` value that is not an array, holds an unknown id, holds a duplicate, or
  carries `on: 1` → `normaliseFieldList`'s existing five steps, unchanged
- **the four keys are gone from the prefs blob after a `savePrefs`, and `lineShape`
  is still there**
- `savePrefs` and the presets writer are still read-modify-write, so a tab open since
  this morning cannot write a stale list over a preset created since (§2.5)
